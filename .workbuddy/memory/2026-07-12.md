## 歌曲分类逻辑修复

用户反馈歌曲分类存在三个问题：区分逻辑有误、容易卡住、反应速度过慢。

### 根因诊断

1. **UI 卡死根因**：`_capture_and_detect` 虽然开了 worker 线程，但 worker 只做窗口激活后 emit `window_activated` signal，真正的 PaddleOCR 推理在 `_on_window_activated` slot（主线程）中执行，1-3 秒的 OCR 期间整个 UI 完全冻结。

2. **速度慢根因**：`_read_tracks_full` 对整张图做一次 OCR 后，`_refine_song_names` 又对歌曲列放大 3 倍做第二次 OCR，每次检测调用两次 PaddleOCR。

3. **区分逻辑缺陷根因**：position 模式用 20px 固定分桶且只取最上面一行（`min(rows.keys())`），区域内有换行或残留文本时取错；position 模式缺少 header 过滤；无歌曲去重。

### 修改文件

- `gui/main_window.py`：将 OCR 逻辑从 `_on_window_activated`（主线程 slot）合并到 `_capture_and_detect` 的 worker 线程；删除 `_on_window_activated` 方法和 `window_activated` signal 连接；`_handle_track_detected` 增加歌曲去重（同名同艺人跳过 UI 更新但仍启用按钮）。
- `core/ocr_reader.py`：position 模式去掉 20px 分桶 + 仅取首行逻辑，改为直接合并区域内所有非 header 文本；position 模式增加 header 过滤；删除 `_refine_song_names` 方法及相关常量 `SONG_CROP_X_MAX`/`SONG_CROP_SCALE`；移除不再使用的 `import cv2`。
- `core/screen_capture.py`：`activate_window` 的 sleep 从 500ms 减至 300ms，fallback 从 200ms+500ms 减至 150ms+300ms。
- `CHANGELOG.md`：新建文件记录本次变更。
- `AGENTS.md`：更新 OCR 描述（删除二次 OCR 说明，增加线程安全注意事项）。

## 音频检测修复 ("Apple Music 未在播放" 误判)

用户反馈应用显示"Apple Music 未在播放"，但 Apple Music 实际正在播放。

### 根因诊断

1. **RMS 阈值过高**：`SILENCE_RMS_THRESHOLD = 0.008`（约 -42dB），低音量播放时 RMS 可能低于此阈值，连续 3 次后触发 `no_audio`。
2. **WAV 格式严格限制**：`_parse_wav_header` 只接受 32-bit float stereo（audio_format=3, ch=2, bits=32），其他格式直接返回 None，导致 header 永不解析、音频数据永不存储。如果 process-audio-capture 输出 16-bit int 等格式，整个音频管道静默失败。

### 修改文件

- `core/audio_capture.py`：
  - `__init__` 增加 `_audio_format`/`_num_channels`/`_sample_rate`/`_bits_per_sample` 实例变量。
  - `_parse_wav_header` 改为接受任意 WAV 格式，存储格式信息并输出日志（不再因格式不匹配返回 None）。
  - `_store_pcm` 根据 format/bits/channels 选择解码方式：16-bit int、24-bit int、32-bit int、32-bit float；mono 复制为 stereo，多声道取前两路。
  - `_pipe_reader` 增加管道连接和数据接收日志。
  - `AudioSample.sample_rate` 使用从 header 解析的实际采样率（不再硬编码 48000）。
- `core/audio_analyzer.py`：`SILENCE_RMS_THRESHOLD` 从 0.008 降至 0.003；`_analysis_loop` 增加静音 RMS 值日志。

## Code Review 修复

对上述全部修改进行自审，发现并修复 7 个问题：

1. **WAVEFORMATEXTENSIBLE (0xFFFE) 未解析 subformat tag** — 放宽 `_parse_wav_header` 时遗漏了 extensible 格式的子格式提取，恢复解析 subformat tag (offset+32..36) 映射为 format=3/1。
2. **采样率硬编码 48000** — `_max_buffer_samples`、`get_snapshot`、`_analyze_chunk` 三处硬编码，改为用 `self._sample_rate` / `self._capture.sample_rate`。在 `_parse_wav_header` 成功时更新 `_max_buffer_samples`。
3. **24-bit int 解码用 Python for 循环** — 48kHz stereo 约 96000 次/秒 `int.from_bytes`，改为 numpy 向量化（reshape + 位运算 + `np.where` 符号扩展）。
4. **`window_activated` signal 死代码** — OCR 移至 worker 后不再 emit/connect，删除定义。
5. **`import sys` 在方法内部** — `_pipe_reader`/`_parse_wav_header`/`_analysis_loop` 三处，统一移到文件顶部。
6. **`_read_tracks_full` 与 `_is_header_text` 之间缺少空行** — 删除 `_refine_song_names` 时遗留的格式问题。
7. **`AudioCaptureManager` 缺少 `sample_rate` 属性** — `AudioAnalyzer` 无法获取实际采样率，新增 `@property sample_rate`。

## 切歌协同优化

用户建议：当音频检测到歌曲特征变化时，检查 OCR 歌曲信息是否也变化，优化切歌协同性。

### 设计

双向协同机制：
- **音频 → OCR**：`boundary_detected` → `_handle_boundary` → 触发 `_capture_and_detect` → OCR 确认歌曲是否变化
- **OCR → 音频**：`_handle_track_detected` 中歌曲变化时调用 `AudioAnalyzer.force_reset()` 重置音频分析状态

### 修改文件

- `core/audio_analyzer.py`：新增 `force_reset()` 公开方法（调用 `_reset_state()`，不 emit `boundary_detected` 避免循环）。
- `gui/main_window.py`：
  - `__init__` 增加 `_detecting` 和 `_classifying` 状态标志。
  - `_capture_and_detect` 增加 `_detecting` 防重入检查 + `finally` 清除。
  - `_handle_boundary` 中，`_running` 且不在分类中时触发 OCR 确认。
  - `_handle_track_detected` 中，歌曲变化时调用 `force_reset()`。
  - `_on_classify` 中设置 `_classifying = True` + `finally` 清除。

## 音频情绪算法优化

用户反馈：明显欢快的歌被判定为 TENSE。根因：librosa 回退路径 valence 计算系统性偏低。

### 根因和修复

1. **NORM_HARMONIC 1.5→0.6** — harmonic_ratio 实际 0.2-0.6，除以 1.5 后归一化值仅 0.13-0.40。
2. **rms_norm 负权重 -0.10→-0.03** — 欢快歌响度高被惩罚 -0.07 直接拉负 valence。
3. **valence 偏移 0.30→0.20** — 需 valence_raw>=0.30 才能正 valence，实际欢快歌仅 0.25-0.40。
4. **lock 后不记录 quadrant 历史** — `if not self._locked` 条件导致错误锁定后无法自我纠正，改为始终记录。
5. **arousal 微调** — rms 0.25→0.20, onset 0.15→0.20（安静快速的歌应高 arousal）。
6. **BOUNDARY_THRESHOLD_LOCKED 1.2→1.0** — 1.2 是 VA 空间对角线的 42% 偏高。
7. **测试用例更新** — 四个 quadrant 用真实音乐特征值范围。
